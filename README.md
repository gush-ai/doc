# How to build a provider — full walkthrough

This is the complete, guided version of `/services/README.md`. Read that
first for the quick map; come here for the full contract, worked examples,
and a pre-launch checklist.

## 1. Copy the starter kit

```
cp -r services/_template-starter services/my-provider
```

Rename `key`, `name`, `command` in `manifest.php` to match, and flip
`enabled` to `true` only once you've finished testing.

## 2. `manifest.php` — full field reference

```php
<?php
declare(strict_types=1);

return [
    // --- identity ---
    'key'         => 'my-provider',       // must match the folder name
    'name'        => 'My Provider',       // shown in the store/UI
    'command'     => '@myprovider',       // what users type in chat
    'type'        => 'generic',           // 'ecommerce' | 'media' | 'bridge' | 'sports' | 'generic'
    'description' => 'One-line summary for the store card.',
    'handler'     => 'generate.php',
    'enabled'     => true,

    // --- access ---
    'requires_login' => true,

    // --- billing (leave all 0 to stay free) ---
    'free_limit'        => 0,
    'price_ngn'         => 0.00,
    'free_window_hours' => 24,

    // --- what the store/chat UI shows ---
    'ui' => [
        'icon'    => 'fa-solid fa-plug',       // any Font Awesome class
        'actions' => ['search', 'get_details'], // REAL callable actions, not marketing copy
    ],
    'permissions'      => ['Reads public data only.'],
    'developer'        => ['name' => 'Your Name', 'url' => '', 'support_email' => ''],
    'long_description' => 'The full paragraph shown in the details modal.',

    // --- visibility (see section 4) ---
    'visibility'    => 'public',   // or 'private'
    // 'owner_user_id' => 482,     // required if visibility is 'private'

    // --- per-user connections (see section 5) ---
    'requires_install'          => false,
    'supports_multi_connection' => false,

    // --- optional custom design (see section 6) ---
    'template' => ['enabled' => false],
];
```

## 3. `generate.php` — the handler contract

```php
<?php
declare(strict_types=1);

return function (array $ctx = []): array {
    $input = $ctx['input'] ?? [];
    $action = strtolower(trim((string)($input['action'] ?? 'default')));

    switch ($action) {
        case 'search':
            // ... do the work, call an external API, whatever ...
            return ['ok' => true, 'results' => []];
        default:
            return ['ok' => false, 'error' => "Unknown action \"$action\"."];
    }
};
```

Rules:
- Always `return ['ok' => true, ...]` on success or `['ok' => false, 'error' => '...']` on failure — `main.php`'s `service_run` checks `$result['ok']` and surfaces `$result['error']` verbatim to the user.
- Never call `exit`/`die`/`echo` directly — you're a function, not an endpoint. `main.php` handles the JSON response and billing wrapper.
- For a shopping-shaped result, return `['ok' => true, 'products' => [...]]` — the default card/modal renderer picks it up automatically. Each product: `id`, `name`, `price`, `image_url`, `available_quantity` (optional).
- For a media/track-shaped result on a provider with `'type' => 'media'`, the modal automatically shows Play/Play next/Queue instead of Add to cart/Buy now — no extra flag needed, it's driven by the manifest's `type`.

## 4. Public vs. private providers

Two independent things are both called "private" in this framework — don't
conflate them:

**A provider itself can be private** (only one specific person can see or
run it at all):
```php
'visibility' => 'private',
'owner_user_id' => 482,
```
Use this for a provider one person built for themselves that shouldn't
appear in anyone else's store. `service_run`, `service_catalog`, and
`get_available_services` all enforce this — a 404 for everyone else, so
its existence isn't leaked either.

**A provider can be public but each user's connection to it is private**
(everyone can install it, but what they connect is theirs alone) — that's
`requires_install`, covered next. This is the far more common case for
things like "connect your own WordPress/Shopify/whatever."

Don't set `visibility: private` just because a provider handles user data —
that's what `requires_install` + `user_service_installs` is for.

## 5. Providers that connect to a user's own account

Set:
```php
'requires_install'          => true,
'supports_multi_connection' => true, // or false if one connection is enough
```

Then build a connect form in the frontend (see `openWordpressConnectForm`/
`submitWordpressConnect` in `main12.js` for the reference implementation)
that POSTs to `?action=service_install`:

```js
await fetch('?action=service_install', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    service: 'my-provider',
    label: 'My Site',           // optional, shown in "Installed" state
    config: { api_key: '...' }  // whatever your generate.php needs — any JSON object
  })
}).then(r => r.json());
// -> { ok: true, install_key: "my-provider_482_gush_ai_9f3a1c02b7de" }
```

`main.php` stores `config` **encrypted at rest** (AES-256-CBC, keyed off
`GOS_SI_SECRET` — set this as a real secret in production; see
`service_installer.php`'s header comment for exactly what this does and
doesn't protect against) and, on every `service_run` call, decrypts it and
hands it to your `generate.php` as `$ctx['install']['config']`:

```php
$config = $ctx['install']['config'] ?? [];
$apiKey = $config['api_key'] ?? '';
```

Your `generate.php` never reads or writes `user_service_installs` directly
— `main.php` and `service_installer.php` are the only things that touch
that table. This is deliberate: it's the one place credential handling is
audited, so every provider gets the same guarantees for free.

To let a user remove a connection:
```js
await fetch('?action=service_uninstall', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ install_key: theKey })
});
```

## 7. Pre-launch checklist

Before flipping `enabled => true` on anything with `visibility => 'public'`:

- [ ] Every branch of `generate.php` returns `['ok' => bool, ...]` — never lets a PHP warning/notice leak into the JSON response.
- [ ] Any external HTTP call sets a timeout (`CURLOPT_TIMEOUT`) — see `wordpress-gateway/generate.php`'s `gwgHttp()` for the pattern.
- [ ] `permissions` in the manifest actually lists everything the provider can do — this is shown to users before they install, don't undersell it.
- [ ] If `requires_install`, every field you read from `$ctx['install']['config']` has a safe default (`?? ''`) — don't assume the user filled in every field correctly.
- [ ] `ui.actions` lists only actions that are really implemented in `generate.php`'s `switch` — the store's "Commands / features" list is generated straight from this array.
- [ ] Ran a manual `?action=service_run` call for every action in `ui.actions` and confirmed the response shape.
